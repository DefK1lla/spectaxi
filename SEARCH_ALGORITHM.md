# Поиск исполнителей

Как собирается выдача машин для клиента. Сценарий — `USER_SCENARIOS.md`.

## 1) Сначала фильтр заказа

Клиент заполняет (экран фильтра / черновик / будущий заказ), затем ищет.

| Поле | Обязательно | Смысл |
| --- | --- | --- |
| `category_id` | да | тип транспорта из `machinery_categories` |
| `pricing_type` | да | тариф, разрешённый категории |
| `quantity` | да | часы / смены / сутки / месяцы / рейсы / км |
| `search_mode` | да | `urgent` или `planned` |
| `planned_start_on` | только для `planned` | дата начала (без времени окончания) |
| `lat`, `lng` | да | точка работ (для расстояния) |
| `max_amount` | нет | потолок посчитанной цены |
| `radius_km` | нет | фильтр по дистанции |

У `urgent` **нет** даты начала и **нет** даты окончания.  
У `planned` есть **только дата начала**, без даты/времени окончания.

Клиент не задаёт пару «начало + конец» отдельно от тарифа. Длительность для занятости считает сервер из тарифа × количества (раздел 2.1). Стоимость по карточке: `base_rate × quantity`. Сумму клиент не вводит.

## 2) Кого показываем

Карточка выдачи — **единица транспорта**. Занятая единица в списке и на карте **не показывается**. Другие свободные единицы того же исполнителя показывать можно.

Единица попадает в выдачу, если одновременно:

- не удалена;
- категория совпадает;
- есть активный тариф нужного `pricing_type`;
- у владельца `accepts_orders = true`;
- если `executor_subscription_enabled` — подписка `active` (пока флаг выключен, проверка не действует);
- если у категории `license_category` не пустой — у исполнителя лицензия на **эту категорию** в статусе `approved`;
- окно запроса клиента **не пересекается** с занятостью **этой единицы** (раздел 2.1–2.2);
- не своя машина;
- не исполнитель с `declined` / `expired` / `negotiation_rejected` / `terms_expired` по `exclude_for_order_id` (поиск в рамках существующего заказа);
- если задан `max_amount` — `base_rate × quantity ≤ max_amount`;
- если задан `radius_km` — дистанция ≤ радиуса.

Черновики и `published` слот **не блокируют**: два запроса на одно время могут одновременно висеть у одного исполнителя. Слот занимает только заказ после первого «принять» (`in_negotiation` и дальше). Что происходит, если исполнитель принял один из двух — `ORDER_STATE_MACHINE.md`.

### 2.1) Окно запроса клиента

Сервер считает `occupancy_start_at` … `occupancy_end_at` для сравнения со занятыми заказами.

| Режим | Начало окна | Конец окна |
| --- | --- | --- |
| `urgent` | момент поиска / отправки запроса (`now`) | начало + длительность из тарифа × количества |
| `planned` | `00:00` даты `planned_start_on` в локали точки работ | начало + длительность из тарифа × количества |

Длительность для занятости (это не цена, цена по-прежнему ставка × количество):

| `pricing_type` | Длительность |
| --- | --- |
| `hour` | `quantity` часов |
| `shift` | `quantity × 8` часов |
| `day` | `quantity` суток (24 ч) |
| `month` | `quantity × 30` суток |
| `trip` | календарный день начала окна |
| `km` | календарный день начала окна |

У заказа эти поля хранятся (сервер пересчитывает при смене тарифа, количества, режима или даты).

### 2.2) Когда единица занята

Единица занята, если окно клиента пересекается с окном **другого заказа этой единицы** в статусах `in_negotiation`, `awaiting_payment`, `in_progress`, `disputed`.

Если время занято — единица в выдаче нет.

## 3) Сортировка и фильтры

Список: **по расстоянию** от точки работ до локации машины, по возрастанию (первый — ближайший).

При одинаковом расстоянии (округление до 0.1 км) — меньшая посчитанная цена.

Внутренний рейтинг в сортировке **не используется** и в UI не показывается.

Клиент сужает выдачу фильтрами (это параметры того же запроса, не отдельный ранжирующий ключ):

- расстояние (`radius_km`);
- потолок цены (`max_amount`).

Смена тарифа, количества, режима или даты начала — перезапрос: занятость и цена пересчитываются на сервере.

## 4) Карта

Те же элементы, без своей сортировки. Точки с одинаковыми координатами — счётчик `+N`, по клику список машин точки. Занятые единицы на карте тоже не рисуются.

## 5) Запрос после выбора

`POST /orders` (или отправка из черновика) с `machinery_unit_id`, копией фильтра и `computed_amount` на момент отправки. Дальше матчинг — один ожидающий кандидат, 5 минут, как в `ORDER_STATE_MACHINE.md`.
