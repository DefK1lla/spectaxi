# Технический стек и план запуска

Разработчик один, пишет на TypeScript. Цель — запуститься бесплатно и потом платить только за то, что реально нагружено, без переписывания кода.

Цены ориентировочные, на октябрь 2026. Перед подключением сверяйтесь с сайтом сервиса.

## 2) Правило мягкого перехода

Переход с бесплатного на платное должен сводиться к смене переменных окружения и переносу данных. Для этого:

- API и админка собираются в **Docker-образ**. Один и тот же образ работает на бесплатном PaaS и на своём VPS.
- База — **обычный PostgreSQL** без фич конкретного провайдера. Перенос — `pg_dump` / `pg_restore`.
- Файлы — только через **S3 API**. Смена хранилища — новые `S3_ENDPOINT` / ключи + копирование бакета (`rclone sync`).
- Очередь — в том же PostgreSQL (pg-boss). Отдельный сервис очередей переносить не нужно.
- Карта — URL стиля в конфиге приложения (`MAP_STYLE_URL`). Смена подложки — новый URL, без релиза кода (через EAS Update).
- Все внешние ключи (DaData, ЮKassa, Telegram, SMS) — в переменных окружения API. В приложении ключей нет.
- Метрики — стандартный формат Prometheus на `/metrics`. Сменить, кто их читает (Grafana Cloud → свой Prometheus), можно без изменений в коде.



## 3) Структура репозитория

Монорепо на pnpm workspaces:

```
apps/
  api/      NestJS: REST /api/v1, вебхуки ЮKassa, фоновые задачи
  admin/    Next.js: лицензии, споры, блокировки, отмена заказов, разбор other
  mobile/   Expo: клиент и исполнитель в одном приложении (current_mode)
packages/
  contracts/  общие типы и zod-схемы запросов/ответов API
```

`contracts` — главный выигрыш от единого языка: API, админка и приложение используют одни и те же типы.

## 6) Как устроены ключевые части



### Вход по телефону

1. `POST /auth/request-code` → API генерирует код, хранит хэш и срок жизни в PostgreSQL.
2. Отправка: Telegram Gateway → если не доставлен, SMS.
3. Ограничения: не чаще одного кода в минуту на номер, лимит в час на номер и на IP. Без этого SMS-бюджет съедят боты.
4. `POST /auth/verify-code` → JWT access (короткий) + refresh (длинный, хранится в БД, можно отозвать при блокировке).
5. После входа приложение регистрирует push-токен устройства (`PUT /users/me/push-devices`).

### Вход в админку

Отдельные учётные записи `admin_users`: email + пароль + одноразовый код из приложения-аутентификатора (TOTP, библиотека `otplib`). Админов заводит команда на сервере, регистрации нет. Токен админа выпускается с отдельным `audience` — API не пустит пользовательский токен в `/admin/*` и наоборот.



### Таймеры заказа

Все дедлайны из `ORDER_STATE_MACHINE.md` (5 минут, сутки, 24 часа без активности, дата начала планового):

- при наступлении события ставится отложенная задача pg-boss (`startAfter`);
- задача при срабатывании перечитывает заказ и проверяет, что статус и версия не изменились, иначе ничего не делает;
- раз в минуту отдельная задача-«подметальщик» ищет просроченные дедлайны по индексам (`response_deadline_at`, `terms_confirm_deadline_at` и т.д.) — на случай перезапуска сервера.

Переходы статусов — в транзакции с блокировкой строки заказа (`SELECT … FOR UPDATE`). Так решаются гонки «принять vs таймаут» и автоотказ остальных срочных запросов.

### Поиск

PostgreSQL без PostGIS: сначала грубый фильтр по прямоугольнику вокруг точки (индекс по `location_lat`, `location_lng`), затем точное расстояние по формуле гаверсинуса, сортировка по расстоянию и цене. PostGIS подключить, когда выдача станет медленной (проверьте, что хостинг поддерживает расширение).

### Файлы

1. Приложение перед отправкой уменьшает фото (`expo-image-manipulator`, длинная сторона ~1600 px) — так запрос весит сотни килобайт, а не мегабайты.
2. Отправляет файлы в API `multipart/form-data`, как в `API_CONTRACT_MVP.md`.
3. API проверяет тип и размер, при необходимости пережимает (`sharp`), кладёт в S3 и сохраняет запись.

Фото машин и аватары — в публичном бакете (ссылка в ответах API). Документы лицензий и фото из споров — в приватном бакете, отдаются только по временной ссылке.

### Оплата

Используется «Безопасная сделка» ЮKassa, а не обычный двухстадийный платёж: тот живёт от 2 часов до 7 дней, а заказ на месяц длится дольше. Сделка держит деньги до 180 дней.

**Карта исполнителя для выплат** (один раз, в профиле):

1. Приложение открывает в WebView страницу с виджетом выплат ЮKassa.
2. Исполнитель вводит карту, виджет отдаёт синоним карты (`payout_token`) и маску.
3. Приложение отправляет их в `PUT /executor/payout-card`. Номер карты к нам не попадает.

**Оплата заказа:**

1. `create-payment` → API создаёт сделку (`POST /v3/deals`) и платёж в неё на `amount_to_pay` = `computed_amount` + комиссия сделки (`POST /v3/payments` с `deal.id`). Процент комиссии — переменная `SECURE_DEAL_FEE_PERCENT`, подбирается так, чтобы покрыть комиссию ЮKassa с НДС.
2. Приложение открывает `confirmation_url` во встроенном браузере, возврат по `spectaxi://payment-return`.
3. Статус меняет **только вебхук**, не возврат в приложение. ЮKassa уведомления не подписывает: принимаем запросы только с её IP-адресов и перезапрашиваем объект через API, верим ответу API. Идемпотентность — по id события.
4. Оплата прошла → деньги на балансе сделки (`authorized`) → заказ `in_progress`.
5. `completed` → выплата исполнителю на `computed_amount` (`POST /v3/payouts` с `deal.id` и `payout_token`) → `captured`, ЮKassa закрывает сделку.
6. Отмена, возврат в поиск, правка на `awaiting_payment`, решение админа «вернуть» → возврат клиенту (`POST /v3/refunds` с `deal.id`).
7. Сделку никто не закрыл за 180 дней → ЮKassa сама возвращает деньги клиенту, приходит уведомление, заказ → `disputed`.

При возврате клиенту ЮKassa возвращает всю сумму, включая комиссию сделки, а свою комиссию за эквайринг списывает с баланса магазина. Значит, каждая отмена оплаченного заказа стоит платформе около 4–5% его суммы.

Нативный SDK ЮKassa не нужен: обёртки под React Native сторонние и ломаются при обновлениях iOS/Android. Вернуться к вопросу, только если конверсия оплаты через браузер окажется низкой.

### Карта и адреса

- Карта рисует только подложку и маркеры машин. Группировка маркеров с одинаковыми координатами (`+N`) — на клиенте.
- Ввод адреса: поле с подсказками DaData через API → выбранная подсказка даёт адрес и координаты.
- Тап по карте → `GET /geo/reverse` → `geolocate` DaData → адрес.
- Публичный Nominatim OpenStreetMap для автокомплита **не использовать**: его правила запрещают автокомплит и ограничивают нагрузку одним запросом в секунду.



### Мониторинг

Sentry ловит ошибки, логи смотрим в консоли платформы, UptimeRobot сообщает «сервер лежит». Метрики нужны для того, что не видно в ошибках: тихо не сработавших таймеров, зависших платежей, расходов.

| Метрика | Алерт | Зачем |
| --- | --- | --- |
| Отставание очереди pg-boss, число просроченных дедлайнов заказа | Просрочка дольше 2 минут | Таймеры 5 минут и суток — основа штрафов и статусов |
| Ошибки обработки вебхуков ЮKassa; платежи в `pending` / `authorized` без движения | Любая ошибка вебхука; выплата не прошла | Деньги |
| Отправленные коды входа по каналам (Telegram / SMS) в час | Резкий рост | Расходы и признак атаки ботов |
| Запросы к DaData за сутки | 80% от 10 000 | Бесплатный лимит |
| Время ответа `GET /search/machinery` (p95) | Выше 600 мс | Требование из `API_CONTRACT_MVP.md` §12 |
| Ответы API 5xx, время ответа по маршрутам | Доля 5xx выше 1% | Общее здоровье |

В метках метрик — только маршруты, статусы и каналы. Телефонов, имён, адресов и id пользователей нет: Grafana Cloud хранит данные за рубежом, а персональные данные должны оставаться в РФ.

## 7) Порядок работ

1. Монорепо, `contracts`, Nest-каркас, Prisma, деплой «hello» на DADA Cloud и Vercel. Сразу `/health`, `/metrics`, Sentry, монитор UptimeRobot.
2. Вход по телефону (dev-код), профиль, режимы, вход в админку.
3. Категории, парк, загрузка фото в R2, лицензии + экран лицензий в админке.
4. Поиск и карта в приложении, подсказки адресов.
5. Заказы: запрос, принять/отклонить, переговоры, таймеры, автоотказ.
6. ЮKassa на тестовом магазине: карта для выплат, сделка, оплата, вебхуки, выплата, возвраты.
7. Завершение, отзывы, рейтинг, уведомления.
8. Споры и остальная админка: блокировки, отмена заказа, разбор `other`.
9. Фаза 1: аккаунты магазинов приложений, Telegram Gateway + SMS, домен, TestFlight и внутреннее тестирование Google Play, заявка в ЮKassa на боевой магазин и «Безопасную сделку».
