# Поиск исполнителей

Как собирается выдача машин для клиента. Сценарий — `USER_SCENARIOS.md`.

Жёсткого календаря (запрет слотов) нет — **отложено** до боли на проде или явного решения (`PRODUCT_FOUNDATION.md` §17). Сейчас: заказчик задаёт **окно работ**; скрытие занятых в выдаче + мягкое предупреждение при принятии (запрета нет). Для срочного дополнительно — флаг «принимаю срочные заказы». Подробности — §6.

Матч — по **точке заказа и расстоянию до машины**, не по стране телефонного номера клиента/исполнителя. Фильтра «только исполнители с тем же префиксом номера» нет.

## 1) Сначала фильтр заказа

Клиент заполняет (экран фильтра / черновик / будущий заказ), затем ищет.

| Поле               | Обязательно                                         | Смысл                                                                          |
| ------------------ | --------------------------------------------------- | ------------------------------------------------------------------------------ |
| `category_id`      | да                                                  | тип транспорта из `machinery_categories`                                       |
| `pricing_type`     | да                                                  | тариф, разрешённый категории                                                   |
| `quantity`         | да                                                  | часы / смены / сутки / месяцы / рейсы / км                                     |
| `search_mode`      | да                                                  | `urgent` или `planned`                                                         |
| `planned_start_at` | только для `planned`                                | начало окна работ                                                              |
| `planned_end_at`   | обязательно для `planned`; для `urgent` опционально | конец окна («завершить к …»); должен быть позже начала (у planned) / в будущем |
| `lat`, `lng`       | да                                                  | точка работ (для расстояния)                                                   |
| `description`      | нет                                                 | свободный текст для исполнителя, на выдачу не влияет                           |
| `max_amount`       | нет                                                 | потолок посчитанной цены                                                       |
| `radius_km`        | нет                                                 | фильтр по дистанции                                                            |

У `planned` обязательны начало и конец окна. У `urgent` начала нет; конец («нужно к») опционален. Длительность из тарифа×quantity на занятость **не** влияет — только эти поля.

Стоимость по карточке: `machinery_pricing_rules.base_rate` выбранного тарифа × `quantity`. Клиент сумму не вводит. Какие тарифы вообще доступны — задаёт тип транспорта (`TARIFF_TYPES.md`): у одних часы/смены/месяцы, у других километры и рейсы.

## 2) Кого показываем

Карточка выдачи — **единица транспорта**: фото, локация, расстояние, посчитанная цена, имя и аватар исполнителя, средняя оценка и число публичных отзывов. Контактов нет.

Единица попадает в выдачу, если одновременно:

- не удалена;
- категория совпадает;
- есть активный тариф нужного `pricing_type`;
- если `search_mode = urgent` — у владельца `accepts_urgent_orders = true`; для `planned` флаг не проверяется;
- если `executor_subscription_enabled` — подписка `active` (пока флаг выключен, проверка не действует);
- у исполнителя лицензия на **эту категорию** в статусе `approved` (тип лицензии у категории обязателен);
- не своя машина;
- не исполнитель с `declined` / `auto_declined` / `expired` / `negotiation_rejected` / `terms_expired` по `exclude_for_order_id` (поиск в рамках существующего заказа);
- если задан `max_amount` — `base_rate × quantity ≤ max_amount`;
- если задан `radius_km` — дистанция ≤ радиуса;
- исполнитель **не занят** по правилу окон §6 относительно окна **этого** поиска/заказа.

Один исполнитель может одновременно получить несколько запросов от разных клиентов (если окна не выкинули его из выдачи); при принятии срочного — автоотказ других срочных `notified` — `ORDER_STATE_MACHINE.md` §6.1.

## 3) Сортировка и фильтры

Список: **по расстоянию** от точки работ до локации машины, по возрастанию (первый — ближайший).

Дистанцию считает сервер. На проде — **PostGIS**; на урезанном dev без extension — bbox + гаверсинус. Для клиента и контракта API разницы нет (`TECH_STACK.md`).

При одинаковом расстоянии (округление до 0.1 км) — меньшая посчитанная цена.

Внутренний рейтинг в сортировке **не используется** и в UI не показывается.

Клиент сужает выдачу фильтрами (это параметры того же запроса, не отдельный ранжирующий ключ):

- расстояние (`radius_km`);
- потолок цены (`max_amount`).

Смена тарифа или количества в фильтре поиска — перезапрос выдачи по текущим ставкам. После отправки запроса цена в заказе живёт по снимку ставки (`PRODUCT_FOUNDATION.md` «Цена заказа»). Смена окна (`planned_start_at` / `planned_end_at`) — перезапрос выдачи (занятость §6).

## 4) Карта

Те же элементы, без своей сортировки. Точки с одинаковыми координатами — счётчик `+N`, по клику список машин точки.

## 5) Запрос после выбора

Новый заказ — `POST /orders` с `machinery_unit_id`, копией фильтра и режимом расчёта; цена фиксируется по текущей ставке машины. Внутри существующего заказа в `published` (опубликованный черновик, возврат в поиск) — `POST /orders/{id}/request-executor`, выдача запрашивается с `exclude_for_order_id`. Дальше матчинг — один ожидающий кандидат на заказ, 5 минут, как в `ORDER_STATE_MACHINE.md`.

Заказ в `published` без ожидающего кандидата система снимает сама: срочный через 24 часа без действий клиента, плановый при наступлении даты начала.

## 6) Окно работ, занятость и предупреждение

Заказчик задаёт, **к какому моменту** работа должна быть закончена. Система **не** запрещает пересечения — исполнитель сам решает, принимать ли; при пересечении показываем предупреждение.

### 6.1) Окно заказа

Полуинтервал `[window_start, window_end)` без буфера.

| Режим                       | `window_start`                                                                                                                   | `window_end`                           |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| `planned`                   | `planned_start_at`                                                                                                               | `planned_end_at` (обязателен, > start) |
| `urgent` с указанным концом | момент, с которого заказ «занял» исполнителя: `accepted_at` кандидата, иначе время перехода в `awaiting_payment` / `in_progress` | `planned_end_at`                       |
| `urgent` без конца          | нет конечного окна (см. особый случай ниже)                                                                                      | —                                      |

Окно **поиска** (ещё нет заказа или черновик): для `planned` — те же поля фильтра; для `urgent` с «нужно к» — `[now, planned_end_at)`; для `urgent` без конца — точка `now` (пересечение = «сейчас внутри чужого окна»).

### 6.2) Какие заказы считаются занятостью

Заказы исполнителя (по **любой** его машине), где он уже «в деле» и физически может быть нужен на объекте:

| Статус                                            | Включаем                                          |
| ------------------------------------------------- | ------------------------------------------------- |
| `notified`                                        | нет (ещё не принял)                               |
| `in_negotiation`                                  | да (принял)                                       |
| `awaiting_payment`                                | да (условия подтверждены, ждут оплату)            |
| `scheduled`                                       | да                                                |
| `in_progress`                                     | да                                                |
| `disputed`                                        | да, пока есть `open` спор (ещё не закрыт админом) |
| `completed` / `cancelled` / `draft` / `published` | нет                                               |

### 6.3) Скрытие в поиске

Исполнитель **не попадает в выдачу**, если окно **нового** поиска/заказа **пересекается** с окном любого его заказа из §6.2 (по любой машине).

Особый случай: срочный **без** `planned_end_at` в статусе `in_progress` или `disputed` — считаем занятым «с сейчас на неопределённый срок»: исполнитель скрыт из **любой** выдачи, пока заказ не `completed` / не закрыт спор в статус без занятости / не `cancelled` по решению админа.

### 6.4) Предупреждение (не блок)

При `POST …/accept` и при «подтвердить условия», если окно **этого** заказа пересекается с другим заказом исполнителя из §6.2:

- ответ/экран содержит предупреждение (код вроде `AVAILABILITY_OVERLAP_WARNING`) и краткий список пересекающихся заказов (id, окна);
- исполнитель может **всё равно** принять / подтвердить;
- клиенту в поиске отдельную пометку «возможно занят» не показываем (занятые уже отфильтрованы §6.3).

Пересечение: `start1 < end2 AND start2 < end1`. Буфера нет.
