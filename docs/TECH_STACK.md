# Технический стек и план запуска

Разработчик один, пишет на TypeScript. Цель — запуститься бесплатно и потом платить только за то, что реально нагружено, без переписывания кода.

Цены ориентировочные, на октябрь 2026. Перед подключением сверяйтесь с сайтом сервиса.

## 2) Правило мягкого перехода

Переход с бесплатного на платное должен сводиться к смене переменных окружения и переносу данных. Для этого:

- API и админка собираются в **Docker-образ**. Один и тот же образ работает на бесплатном PaaS и на своём VPS.
- База — **PostgreSQL**; на проде нужен extension **PostGIS** (не привязка к одному облаку — любой хост с PostGIS). Перенос — `pg_dump` / `pg_restore`. Смена хоста = новый `DATABASE_URL`, код не переписываем.
- Файлы — порт **`ObjectStorage`** в API (`apps/api/src/storage`). Домены не импортируют AWS/S3 SDK. Текущий адаптер — S3-compatible (`S3ObjectStorageAdapter`); смена Neon → R2 → российский S3 = новые `S3_*` (+ при необходимости другой адаптер в `StorageModule`) и `rclone sync` бакета.
- Очередь — в том же PostgreSQL (pg-boss). Отдельный сервис очередей переносить не нужно.
- Карта — URL стиля в конфиге приложения (`MAP_STYLE_URL`). Смена подложки — новый URL, без релиза кода (через EAS Update).
- Все внешние ключи (DaData, ЮKassa, Telegram, SMS) — в переменных окружения API. В приложении ключей нет.
- Метрики — стандартный формат Prometheus на `/api/v1/metrics`. Сменить, кто их читает (Grafana Cloud → свой Prometheus), можно без изменений в коде.

### Где живёт PostgreSQL

API **не** встраивает базу в процесс Node. Prisma подключается по `DATABASE_URL` к отдельному Postgres.

| Среда                         | Где база                                                                                                                  | Как                                                                                                                                                                                                                                |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Локальная разработка (сейчас) | **Neon** Free                                                                                                             | Зарегистрироваться на [neon.tech](https://neon.com), создать project, скопировать connection string в `.env` как `DATABASE_URL`. Серверы не в РФ — только пустой/тестовый dev, без реальных ПДн. Free-tier засыпает после простоя. |
| Локально (альтернатива)       | Postgres в Docker / установленный на машине                                                                               | Тот же `DATABASE_URL` на `localhost`. На слабом ПК не обязателен.                                                                                                                                                                  |
| Прод / закрытый тест с людьми | **Отдельный managed PostgreSQL** (DADA, Timeweb, Selectel, Yandex и т.п.) или Postgres **контейнером рядом с API на VPS** | Не Neon. В РФ, с бэкапами.                                                                                                                                                                                                         |

На проде базу **не обязательно** поднимать через `docker-compose` вместе с бэком, но так можно на VPS:

- **Предпочтительно:** managed Postgres (отдельный сервис) + API в Docker/PaaS. Меньше возни с бэкапами и диском.
- **Допустимо на своём VPS:** `docker compose` с сервисами `api` + `postgres` (+ позже Caddy). База всё равно отдельный контейнер/сервис, не «внутри» Nest — только общая сеть compose и `DATABASE_URL=postgresql://...@postgres:5432/...`.

Смена Neon → managed РФ = новый `DATABASE_URL` + `pg_dump` / `pg_restore` (или migrate на чистую базу).

## 3) Структура репозитория

Монорепо на pnpm workspaces:

```
apps/
  api/      @spectaxi/api — NestJS: REST /api/v1, доменные модули (см. BACKEND_STRUCTURE.md), вебхуки ЮKassa, фоновые задачи
  admin/    @spectaxi/admin — Next.js + FSD: типы лицензий, типы транспорта, лицензии, споры, блокировки, отмена заказов, разбор other
  web/      @spectaxi/web — Next.js + FSD: публичный веб (лендинг / веб-клиент позже); не Expo Web
  mobile/   @spectaxi/mobile — Expo + FSD: клиент и исполнитель в одном приложении (current_mode)
packages/
  contracts/  @spectaxi/contracts — общие типы и zod-схемы запросов/ответов API
  theme/      @spectaxi/theme — дизайн-токены (веб CSS vars + native theme); не UI-kit
  ui/         @spectaxi/ui — Tamagui kit (каркас; compiler — task 13)
```

Имена пакетов: `@spectaxi/*`. Workspace: `pnpm-workspace.yaml` → `apps/*`, `packages/*`.

Локальный запуск из корня:

| Команда              | Что                                     | Порт / URL                                                       |
| -------------------- | --------------------------------------- | ---------------------------------------------------------------- |
| `pnpm dev:api`       | NestJS                                  | `http://localhost:3000/api/v1/health`, `/ready`, `/admin/health` |
| `pnpm dev:admin`     | Next.js админка                         | `http://localhost:3001`                                          |
| `pnpm dev:web`       | Next.js публичный веб                   | `http://localhost:3002`                                          |
| `pnpm dev:mobile`    | Expo                                    | Metro / Expo Go или dev client                                   |
| `pnpm lint`          | ESLint во всех пакетах, где есть скрипт | —                                                                |
| `pnpm typecheck`     | `tsc --noEmit`                          | —                                                                |
| `pnpm test`          | Vitest unit-тесты во всех пакетах       | —                                                                |
| `pnpm test:coverage` | coverage (без fail по %)                | —                                                                |

Переменные окружения: корневой `.env.example` (скопировать в `.env`). Секреты в git не класть.

Mobile: заготовка `apps/mobile/eas.json` (profiles `development` / `preview` / `production`). Для MapLibre позже нужен development build, не Expo Go.

Новые apps подхватываются через `apps/*` — добавить пакет и скрипт `dev:…` в корневой `package.json`.

`contracts` — главный выигрыш от единого языка: API, админка и приложение используют одни и те же типы.

`theme` — один источник визуальных токенов для **admin / web / mobile** (`themeToCssRoot` / `themeToTailwindColors` / `themeToNative`).

`ui` — **Tamagui** (latest). Клиент **пока в `apps/mobile`**; шаринг с web — TBD ([`FRONTEND_SHARE_OPTIONS.md`](FRONTEND_SHARE_OPTIONS.md), task 14). Паритет / mobile-first web / admin desktop-first — [`FRONTEND_FSD.md`](FRONTEND_FSD.md). Токены — `@spectaxi/theme`. Setup — [`tasks/13-tamagui-ui.md`](tasks/13-tamagui-ui.md).

**Почему не gluestack:** v5 dropped Next.js; v4 — legacy. Tamagui поддерживает Next + Expo на актуальной линейке.

Фронтенд (`admin` / `web` / `mobile`): Feature-Sliced Design — [`docs/FRONTEND_FSD.md`](FRONTEND_FSD.md), скилл `.agents/skills/feature-sliced-design`.

## 6) Как устроены ключевые части

### Порты и адаптеры (внешние зависимости)

Правило: **вендорский SDK и HTTP чужого API не протекают в доменные сервисы.** Домен зависит от порта (интерфейс + DI-токен); реализация — адаптер в `providers/` или в инфра-папке (`storage/`, позже аналоги). Смена вендора = новый адаптер + bind в модуле (и env), без поиска по заказам/auth.

**Когда писать код:** порт и первый адаптер — **вместе с фичей**, которая их вызывает. Пустые порты «на вырост» не заводим. Исключение уже сделано: `ObjectStorage` (env есть, загрузки скоро) — образец для остальных.

Каталог (детали размещения — `BACKEND_STRUCTURE.md` § «Порты»):

| Порт (рабочее имя)            | Зачем                             | Адаптеры (план)                                                   | Когда в коде                              |
| ----------------------------- | --------------------------------- | ----------------------------------------------------------------- | ----------------------------------------- |
| `ObjectStorage`               | Фото, документы, signed URL       | S3-compatible (Neon / R2 / РФ S3) — **есть**                      | Каркас есть; вызовы — с парком/лицензиями |
| `OtpSender` / покрытие номера | Вход по телефону, `phone-support` | Dev-код; Telegram Gateway; SMS                                    | Пункт 2 порядка работ (вход)              |
| `PaymentProvider`             | Secure deal, выплаты, webhooks    | ЮKassa (`RUB`); позже — по `currencies.secure_deal_provider_code` | Пункт 6 (оплата)                          |
| `GeoFilter`                   | Радиус и сортировка поиска        | PostGIS; bbox + haversine                                         | Пункт 4 (поиск)                           |
| `AddressDirectory`            | Suggest / reverse                 | DaData; позже — другой провайдер                                  | Пункт 4                                   |
| `PushNotifier`                | Пуши по событиям заказа           | Expo Push                                                         | Когда появятся уведомления (≈ пункт 7)    |
| `JobScheduler`                | Отложенные дедлайны заказа        | pg-boss                                                           | Пункт 5 (таймеры заказов)                 |
| `ImageOptimizer` (опц.)       | Дожим на сервере                  | `sharp` и т.п.                                                    | Вместе с загрузкой фото                   |

Не прячем за отдельный порт без нужды: Prisma (уже driver adapter к Postgres), Sentry, TOTP админки, MapLibre на клиенте.

### Вход по телефону

1. Пока пользователь вводит номер → `GET /auth/phone-support`: API смотрит конфиг **OTP-порта** (адаптеры Telegram Gateway, SMS, в dev — фиксированный код) и отвечает, покрывается ли номер. Нет → UI сообщает, что с такими номерами пока не работаем. Geo-IP / «страна устройства» не используем.
2. `POST /auth/request-code` → та же проверка покрытия; при отказе `PHONE_NOT_SUPPORTED`. Иначе API генерирует код, хранит хэш и срок жизни в PostgreSQL.
3. Отправка: Telegram Gateway → если не доставлен, SMS (в рамках провайдеров, которые приняли номер на шаге 1–2).
4. Ограничения: не чаще одного кода в минуту на номер, лимит в час на номер и на IP. Без этого SMS-бюджет съедят боты.
5. `POST /auth/verify-code` → JWT access (короткий) + refresh (длинный, хранится в БД, можно отозвать при блокировке).
6. После входа приложение регистрирует push-токен устройства (`PUT /users/me/push-devices`).

### Вход в админку

Отдельные учётные записи `admin_users`: email + пароль + одноразовый код из приложения-аутентификатора (TOTP, библиотека `otplib`). Админов заводит команда на сервере, регистрации нет. Токен админа выпускается с отдельным `audience` — API не пустит пользовательский токен в `/admin/*` и наоборот.

### Таймеры заказа

Все дедлайны из `ORDER_STATE_MACHINE.md` (5 минут, сутки, 24 часа без активности, дата начала планового → `scheduled`→`in_progress` или «не найден»). Домен ставит задачи через порт **`JobScheduler`**; адаптер — pg-boss:

- при наступлении события — отложенная задача (`startAfter`);
- задача при срабатывании перечитывает заказ и проверяет, что статус и версия не изменились, иначе ничего не делает;
- раз в минуту отдельная задача-«подметальщик» ищет просроченные дедлайны по индексам (`response_deadline_at`, `terms_confirm_deadline_at` и т.д.) — на случай перезапуска сервера.

Переходы статусов — в транзакции с блокировкой строки заказа (`SELECT … FOR UPDATE`). Так сериализуются одновременные действия по одному заказу. Кто побеждает в спорных парах (принять vs снятие клиентом, отказ vs 5 минут, подтверждение условий vs отмена, оплата vs отмена) — `ORDER_STATE_MACHINE.md`, раздел 7.

### Поиск

**Геопоиск и PostGIS.** Контракт выдачи не меняется (`SEARCH_ALGORITHM.md`: радиус, сортировка по дистанции). Реализация:

1. **Прод и любая «настоящая» БД** (managed / VPS / Docker для закрытого теста) — `CREATE EXTENSION postgis`; точки машин как `geography`/`geometry` + GIST; фильтр радиуса и сортировка через PostGIS (`ST_DWithin` / `ST_Distance`). При выборе хостинга проверять, что extension доступен.
2. **Dev без PostGIS** (если провайдер free-tier не даёт extension) — тот же API: bbox по `location_lat`/`location_lng` + гаверсинус. В коде — порт **`GeoFilter`**, две реализации за флагом/наличием extension, не два разных продукта.
3. Локально предпочтительно сразу Postgres **с** PostGIS в Docker, чтобы путь совпадал с продом.

Колонки `location_lat` / `location_lng` в API и домене остаются; колонка/индекс PostGIS — деталь хранения/запроса.

### Файлы

**Архитектура в API** (см. `BACKEND_STRUCTURE.md` § Object storage):

| Слой             | Что                                                                                                               |
| ---------------- | ----------------------------------------------------------------------------------------------------------------- |
| Порт             | `ObjectStorage` + токен `OBJECT_STORAGE` — `putObject`, `getSignedGetUrl`, `isConfigured`                         |
| Адаптер (сейчас) | `S3ObjectStorageAdapter` (`@aws-sdk/client-s3` + presigner, path-style) — Neon / R2 / Selectel / Yandex / Timeweb |
| Конфиг адаптера  | `S3_ENDPOINT`, `S3_KEY`, `S3_SECRET`, `S3_BUCKET`, `S3_REGION`, `S3_FORCE_PATH_STYLE`                             |
| Bind             | `StorageModule` → `{ provide: OBJECT_STORAGE, useClass: S3ObjectStorageAdapter }`                                 |

Доменные сервисы инжектят только `@Inject(OBJECT_STORAGE)`. Смена провайдера или не-S3 бэкенда — новый адаптер + смена bind, без поиска по доменам.

Поток загрузки:

1. Приложение перед отправкой уменьшает фото (`expo-image-manipulator`, длинная сторона ~1600 px) — так запрос весит сотни килобайт, а не мегабайты.
2. Отправляет файлы в API `multipart/form-data`, как в `API_CONTRACT_MVP.md`.
3. API проверяет тип и размер, при необходимости пережимает (порт **`ImageOptimizer`** / `sharp`), пишет через `ObjectStorage` и сохраняет запись (ключ / URL) в БД.

Фото машин и аватары — в публичном бакете (ссылка в ответах API). Документы лицензий и фото из споров — в приватном бакете, отдаются только по временной ссылке (`getSignedGetUrl`). Позже опционально `S3_BUCKET_PUBLIC` / `S3_BUCKET_PRIVATE`.

### Оплата

Денежные сущности несут `currency` (справочник `currencies`). Порт **`PaymentProvider`** для `secure_deal` выбирается по `currencies.secure_deal_provider_code`. **MVP:** только `RUB` → адаптер ЮKassa. При расширении: новая валюта в справочнике + адаптер, который принимает оплату и выплачивает на карты нужной зоны; кросс-валютные коридоры (платит в одной валюте, получает в другой) отдельно не проектируем, пока не появится вторая валюта. Домен оплаты не импортирует SDK ЮKassa напрямую.

Используется «Безопасная сделка» ЮKassa, а не обычный двухстадийный платёж: тот живёт от 2 часов до 7 дней, а заказ на месяц длится дольше. Сделка держит деньги до 180 дней.

**Карта исполнителя для выплат** (один раз, в профиле):

1. Приложение открывает в WebView страницу с виджетом выплат ЮKassa.
2. Исполнитель вводит карту, виджет отдаёт синоним карты (`payout_token`) и маску.
3. Приложение отправляет их в `PUT /executor/payout-card`. Номер карты к нам не попадает.

**Оплата заказа:**

1. `create-payment` (обязателен `Idempotency-Key`) → API сначала пишет попытку `pending` в БД, затем создаёт сделку (`POST /v3/deals`) и платёж в неё на `amount_to_pay` = `computed_amount` + комиссия сделки (`POST /v3/payments` с `deal.id`). Процент комиссии — переменная `SECURE_DEAL_FEE_PERCENT`, подбирается так, чтобы покрыть комиссию ЮKassa с НДС. После `failed` — новая попытка = новый row; заказ остаётся `awaiting_payment` (`ORDER_STATE_MACHINE.md` §5).
2. Приложение открывает `confirmation_url` во встроенном браузере, возврат по `spectaxi://payment-return`.
3. Статус меняет **только вебхук** (и reconcile), не возврат в приложение. ЮKassa уведомления не подписывает: принимаем запросы только с её IP-адресов и перезапрашиваем объект через API, верим ответу API. Идемпотентность — по id события.
4. Оплата прошла → деньги на балансе сделки (`authorized`). Если заказ ещё `awaiting_payment` → срочный `in_progress` / плановый `scheduled`. Если заказ уже `cancelled` / `published` → автовозврат. Иначе — эскалация по §5.4.
5. `completed` → выплата исполнителю на `computed_amount` (`POST /v3/payouts` с `deal.id` и `payout_token`) → `captured`, ЮKassa закрывает сделку.
6. Отмена, возврат в поиск, правка на `awaiting_payment`, решение админа «вернуть» → возврат клиенту по **живой** попытке (`POST /v3/refunds` с `deal.id`).
7. Сделку никто не закрыл за 180 дней → ЮKassa сама возвращает деньги клиенту, приходит уведомление, заказ → `disputed`.
8. **Регулярный reconcile** (pg-boss, ~каждые 10 мин): выборка зависших `pending` / `authorized` и близких к 180 дням → GET у ЮKassa → тот же apply-path, что webhook (`ORDER_STATE_MACHINE.md` §5.3). Непонятный mismatch → алерт, деньги не трогать. Полный реестр сделок магазина за день — не MVP.

При возврате клиенту ЮKassa возвращает всю сумму, включая комиссию сделки, а свою комиссию за эквайринг списывает с баланса магазина. Значит, каждая отмена оплаченного заказа стоит платформе около 4–5% его суммы.

Нативный SDK ЮKassa не нужен: обёртки под React Native сторонние и ломаются при обновлениях iOS/Android. Вернуться к вопросу, только если конверсия оплаты через браузер окажется низкой.

### Карта и адреса

- Карта рисует только подложку и маркеры машин. Группировка маркеров с одинаковыми координатами (`+N`) — на клиенте.
- Ввод адреса: поле с подсказками DaData через API → выбранная подсказка даёт адрес и координаты.
- Тап по карте → `GET /geo/reverse` → `geolocate` DaData → адрес.
- Публичный Nominatim OpenStreetMap для автокомплита **не использовать**: его правила запрещают автокомплит и ограничивают нагрузку одним запросом в секунду.

### Мониторинг

Sentry ловит ошибки, логи смотрим в консоли платформы, UptimeRobot сообщает «сервер лежит». Метрики нужны для того, что не видно в ошибках: тихо не сработавших таймеров, зависших платежей, расходов.

| Метрика                                                                                     | Алерт                                   | Зачем                                               |
| ------------------------------------------------------------------------------------------- | --------------------------------------- | --------------------------------------------------- |
| Отставание очереди pg-boss, число просроченных дедлайнов заказа                             | Просрочка дольше 2 минут                | Таймеры 5 минут и суток — основа штрафов и статусов |
| Ошибки обработки вебхуков ЮKassa; платежи в `pending` / `authorized` без движения           | Любая ошибка вебхука; выплата не прошла | Деньги                                              |
| `payment_reconcile_mismatch`; залипшие `pending` (>15 мин) / `authorized` после `completed` | Любой mismatch; залипание дольше порога | Потерянный webhook / зависла выплата                |
| Отправленные коды входа по каналам (Telegram / SMS) в час                                   | Резкий рост                             | Расходы и признак атаки ботов                       |
| Запросы к DaData за сутки                                                                   | 80% от 10 000                           | Бесплатный лимит                                    |
| Время ответа `GET /search/machinery` (p95)                                                  | Выше 600 мс                             | Требование из `API_CONTRACT_MVP.md` §12             |
| Ответы API 5xx, время ответа по маршрутам                                                   | Доля 5xx выше 1%                        | Общее здоровье                                      |

В метках метрик — только маршруты, статусы и каналы. Телефонов, имён, адресов и id пользователей нет: Grafana Cloud хранит данные за рубежом, а персональные данные должны оставаться в РФ.

   1a. **Сделано:** monorepo pnpm (`@spectaxi/api`, `admin`, `web`, `mobile`, `contracts`, `theme`, `ui`), `pnpm dev:*` / `lint` / `typecheck` / `test`, Vitest + coverage, CI GitHub Actions, `.env.example`, `eas.json`, Nest `/api/v1`, hello Next + Expo. `@spectaxi/theme` — токены; `@spectaxi/ui` — **Tamagui** + CSS vars; compiler в apps — task 13.

Дальше: свой `DATABASE_URL` из Neon → раскомментировать модуль → миграции по `DOMAIN_MODEL_AND_ERD.md` → `/api/v1/ready` проверяет БД.
   1c. **Сделано (каркас):** `StorageModule` + порт `ObjectStorage` + `S3ObjectStorageAdapter`; env `S3_*` (Neon Object Storage в local/dev). Загрузки доменов ещё нет — вызовы появятся с парком/лицензиями.
