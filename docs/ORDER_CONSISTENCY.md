# Согласованность заказа, кандидата, назначения и платежа (MVP)

Источник переходов статусов — `ORDER_STATE_MACHINE.md`. Здесь — **что должно быть правдой одновременно** в связанных таблицах, и что делать, если разъехалось.

Связанные места: `DOMAIN_MODEL_AND_ERD.md` (сущности и constraints), `API_CONTRACT_MVP.md` §8 (деньги), `SEARCH_ALGORITHM.md` §6 (окна занятости / скрытие в поиске — не статусы таблиц, но влияет, кого можно запросить).

## 1) Коротко

| Таблица             | Роль                                                                        |
| ------------------- | --------------------------------------------------------------------------- |
| `orders`            | главный статус сценария                                                     |
| `order_candidates`  | история запросов исполнителям; не больше одного `notified`                  |
| `order_assignments` | кто закреплён после «подтвердить условия»; **не удаляем** — помечаем снятие |
| `payment_records`   | попытки `secure_deal`; не больше одной живой `pending` \| `authorized`      |

Назначение появляется при «подтвердить условия» (уже на `awaiting_payment` / сразу на `scheduled` или `in_progress` при прямом расчёте).

## 2) Таблица «как должно быть»

«Активное назначение» = строка `order_assignments` с `released_at IS NULL`.
«Живая оплата» = `payment_records` в `pending` или `authorized`.

| Статус заказа      | Кандидат                                                                 | Активное назначение                                                    | Живая оплата (`secure_deal`)                                             |
| ------------------ | ------------------------------------------------------------------------ | ---------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `draft`            | нет                                                                      | нет                                                                    | нет                                                                      |
| `published`        | 0 или 1 × `notified`; остальные — закрытые статусы                       | **нет** (если было — помечено `released_at`)                           | **нет**                                                                  |
| `in_negotiation`   | ровно один `accepted` (текущий)                                          | нет (ещё до confirm-terms)                                             | нет                                                                      |
| `awaiting_payment` | тот же `accepted`                                                        | **да**                                                                 | 0 или 1 живая; можно история `failed` и т.д.                             |
| `scheduled`        | тот же `accepted` (история)                                              | **да**                                                                 | обычно `authorized` (плановый до старта); при `direct_payment` строк нет |
| `in_progress`      | тот же `accepted` (история)                                              | **да**                                                                 | обычно `authorized` (до выплаты); при `direct_payment` строк нет         |
| `completed`        | история                                                                  | **да** (для истории)                                                   | `captured` или строк нет (`direct_payment`)                              |
| `disputed`         | история; ровно один `disputes` со `status=open` (+ опционально закрытые) | **да**, если уже было назначение; иначе нет                            | по ситуации; не должно быть «забытого» `pending` без причины             |
| `cancelled`        | история                                                                  | **да**, если успели подтвердить условия; **нет**, если отменили раньше | нет живой; если была — отменена / возвращена                             |

`direct_payment`: колонка оплаты всегда «нет строк»; логически «не требуется».

## 3) Правила назначения

1. Создать активное назначение — только при успешном «подтвердить условия».
2. Возврат заказа в `published` (неоплата, отклонение партнёра, таймаут условий и т.п.) — **не удалять** строку: поставить `released_at`, причина в `release_reason` / аудите.
3. Новое «подтвердить условия» после нового матча — **новая** строка назначения; старые остаются с `released_at`.
4. На `scheduled` / `in_progress` / `completed` / `disputed` активное назначение не снимаем при нормальном ходе (кроме отмены на `scheduled` — п. 5).
5. Отмена планового на `scheduled`: заказ `cancelled`, назначение **оставляем** для истории; помечаем `released_at`.

На заказ не больше **одного** активного назначения (partial unique: `order_id WHERE released_at IS NULL`).

## 4) Живая оплата vs статус заказа

Живая `pending` / `authorized` допустима **только** пока заказ в `awaiting_payment` или (для `authorized`) уже перешёл в `scheduled` / `in_progress` / дальше по нормальному пути.

Если живая оплата есть, а заказ уже `cancelled` или `published` — это нарушение:

1. применить `ORDER_STATE_MACHINE.md` §5.4 (автовозврат);
2. по возможности не допускать запись такого состояния constraints + проверками в той же TX, что меняет статус заказа;
3. алерт в мониторинг, если починка не удалась.

## 5) Если данные разъехались

Фоновая проверка (sweeper / периодическая джоба) + алерты.

### Простые случаи — автопочинка

| Нарушение                                             | Починка                                                                                                                      |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Заказ `published` / `draft`, есть активное назначение | Поставить `released_at`, аудит `consistency_release_assignment`                                                              |
| Блокировка исполнителя / отзыв лицензии               | Незавершённые заказы → `published` + `released_at` + возврат `authorized`; см. `SERVICE_RULES.md`                            |
| Заказ `published`, есть живая оплата                  | §5.4: отменить/вернуть, статус платежа `cancelled` / `refunded`                                                              |
| Заказ `cancelled`, есть живая оплата                  | §5.4: автовозврат                                                                                                            |
| Заказ не `published`, висит `notified`                | Закрыть кандидата как `withdrawn` (если отмена клиента) или `expired` (если просрочен дедлайн); иначе алерт                  |
| Две живые оплаты на один заказ                        | Оставить новейшую `pending`/`authorized` по правилам денег; лишние `pending` → `cancelled` после сверки с провайдером; алерт |

### Сложные случаи — только алерт (+ ручной разбор)

- Заказ `scheduled` / `in_progress` / `completed` / `disputed`, а **активного** назначения нет.
- Заказ `awaiting_payment`, а активного назначения нет.
- Заказ `scheduled`, а `planned_start_at` уже прошёл и джоба не перевела в `in_progress`.
- Заказ `in_negotiation`, нет кандидата `accepted`.
- `authorized` у провайдера и в БД расходятся после reconcile.
- Любая автопочинка, которая не смогла безопасно завершиться.

Админ в MVP правит через существующие сценарии (отмена, спор, возврат холда), не через «произвольный SQL в UI».

## 6) Транзакции (минимум)

В одной TX с `SELECT … FOR UPDATE` на `orders`:

- смена статуса заказа;
- смена статуса кандидата / создание;
- создание или `released_at` назначения;
- смена статуса **живой** попытки оплаты (когда ещё без внешнего вызова провайдера).

Вызовы ЮKassa — после записи намерения в БД (как в §5.3 FSM); результат — webhook / crash-reconcile / **регулярный** reconcile (~10 мин, тот же apply-path).

## 7) Проверка готовности

- [ ] По каждому статусу из §2 есть интеграционный сценарий «после операции инварианты держатся».
- [ ] Sweeper закрывает простые случаи из §5 и шлёт алерт на сложные.
- [ ] Регулярный payment reconcile догоняет статусы по §5.3 FSM или алертит mismatch.
- [ ] Partial unique: один `notified`; одно активное назначение; одна живая оплата; unique `(order_id, executor_user_id)` на кандидатах.
- [ ] Обязательные constraints из `DOMAIN_MODEL_AND_ERD.md` §5 — в миграциях.
