# Базовая концепция продукта SpexTaxi (MVP)

## 1) Позиционирование продукта

SpexTaxi — мобильный маркетплейс для поиска и заказа спецтехники.

Платформа поддерживает три пользовательских сценария в рамках одной учетной записи:

- частный клиент с разовыми заказами;
- регулярный бизнес-клиент (без обязательной сущности компании в MVP);
- владелец/водитель спецтехники как исполнитель.

Один пользователь имеет один аккаунт и может переключаться между ролями `клиент` и `исполнитель`. Поток заказа у частного и бизнес-клиента одинаковый. Режим интерфейса — одно поле `current_mode`.

## 2) Принципы MVP

- Не проектировать продукт как только B2B.
- Не проектировать продукт как только B2C.
- Не делать оплату в приложении обязательной для всех заказов.
- Разрешать прямую коммуникацию и прямую оплату между пользователями.
- Создавать ценность за счет скорости поиска, качества матчинга, карты, актуальности статусов, уведомлений и истории заказов.
- Считать обход платформы бизнес-риском, но не решать его жесткими техническими запретами.

## 3) Ключевые пользовательские сценарии

Полные шаги — в `USER_SCENARIOS.md`. Кратко:

### Поиск и запрос (клиент)

Фильтр: тип, тариф (набор зависит от типа транспорта — часы/смены/месяцы или километры/рейсы), количество, срочный или плановый (у планового — окно начала и конца работ; у срочного конец опционален), точка, опционально потолок цены. Список ближайших машин, карта с кластерами. Цена на карточке = ставка × количество. Жёсткого календаря нет: занятые по пересечению окон скрыты из выдачи; при accept/confirm — предупреждение, решение за исполнителем (`SEARCH_ALGORITHM.md` §6). По срочным — ещё флаг «принимаю срочные заказы». Контакты после «принять запрос». Один ожидающий запрос на заказ. Черновик можно сохранить без отправки.

### Парк, тарифы и статус (исполнитель)

Тарифы на единицу из списка категории. Тип транспорта — строка `machinery_categories` (`code`, обязательный тип лицензии, текст UI); типы и справочник лицензий ведёт админ. Лицензия — одна на категорию: права + документ на право пользования техникой, без срока; админ верифицирует → `approved`, иначе машина не в поиске. При блоке/отзыве лицензии незавершённые заказы исполнителя → снова поиск + возврат холда. Флаг «принимаю срочные заказы» — ручной чекбокс в профиле. Подписка исполнителя спрятана под `executor_subscription_enabled`.

### Отклик, переговоры, работа

«Принять запрос» открывает контакты (срок подтверждения условий — 1 сутки). «Подтвердить условия» фиксирует посчитанную сумму. Сделка → оплата 1 сутки, иначе возврат в поиск; прямая → срочный сразу в работу, плановый в `scheduled`. Пока сделка не зафиксирована, срыв матча возвращает заказ к поиску; полную отмену до фиксации делает только клиент, исполнитель только отклоняет партнёра. На `scheduled` отмена с причиной у обеих сторон; из `in_progress` — только спор; `completed` когда обе стороны подтвердили исполнение. Заказ без найденного исполнителя система снимает сама (срочный — 24 ч без действий клиента, плановый — дата начала пока ещё `published`).

## 4) Границы домена в MVP

## Входит в MVP

- Профили: после OTP имя и `current_mode`; UI от текущего режима.
- Контакты: Telegram, WhatsApp, MAX и телефон всегда на форме; достаточно одного канала плюс имя.
- Аватар исполнителя, парк, тарифы; в админке — справочник типов лицензий, типы транспорта (с обязательным типом лицензии), одобрение лицензий.
- Поиск по фильтру заказа (`SEARCH_ALGORITHM.md`), черновики заказов.
- Запрос одному; 5 минут (в т.ч. плановый); не ответил = отказ, скрыт; спор; отзывы 1–5 звёзд.
- Цена = тариф × количество; `assigned` нет.
- `scheduled` у планового до даты начала (отмена с причиной); `in_progress` — до подтверждения обеими или спора; отмена начатой работы только спором.
- Безопасная сделка через ЮKassa с первого релиза, опционально для клиента; холд только после реальной оплаты. Исполнитель заранее привязывает карту для выплат в профиле.
- Подписка исполнителя под флагом `executor_subscription_enabled` (в MVP выключен).
- Админка: типы лицензий, типы транспорта, споры, лицензии исполнителей, блокировки, отмена заказа, разбор причин `other` (`SERVICE_RULES.md`, `API_CONTRACT_MVP.md` раздел 9).
- Плановый заказ (окно `planned_start_at`…`planned_end_at`; мягкая занятость по окнам; статус `scheduled` до старта — отмена с причиной; с `planned_start_at` → `in_progress`, дальше только спор).
- Выбор «безопасная сделка» — переключатель на экране отправки запроса, только при включённом флаге.

## Не обязательно для MVP

- Обязательная «Безопасная сделка» для каждого заказа.
- Внутренний кошелек с учетом реальных денег в PostgreSQL.
- Хранение банковских карт на стороне платформы (для выплат храним только синоним карты от ЮKassa и маску номера).
- Полная корпоративная модель (`Company`, `CompanyMember`, `CompanyProject`) до подтвержденной потребности.
- Массовая рассылка одного запроса нескольким исполнителям сразу.
- Запрос своей собственной технике.

## 5) Требования к модели заказа

Каждый заказ должен поддерживать два режима расчета:

- `direct_payment` — условия и оплата согласуются напрямую между сторонами;
- `secure_deal` — опциональная оплата через платежного провайдера.

Каталожные тарифы живут на единице транспорта и задаются исполнителем. Типы: час, смена, сутки, месяц, рейс, километр — какие доступны, зависит от категории (`TARIFF_TYPES.md`).

### Цена заказа (MVP)

- Формула: `computed_amount = unit_rate × quantity`. Минимума заказа, мин. часов и отдельной «доставки на объект» в MVP **нет** (доставка не в каталоге — `TARIFF_TYPES.md`).
- Заказчик сумму не вводит. Комиссия безопасной сделки — сверху, платит клиент (`amount_to_pay`); округление комиссии — вверх до копейки.
- **Снимок ставки:** при отправке запроса конкретной машине сервер копирует `unit_rate` с машины в `order_pricing` и больше **не** подтягивает новые ставки этой машины при правке количества/адреса/описания — пересчёт только `unit_rate × новое quantity`.
- Смена **типа тарифа** (`pricing_type`) в правке — один раз взять актуальную ставку машины для нового типа, записать новый `unit_rate`, дальше снова заморозка.
- Новый запрос другому (или снова тому же после срыва матча) — новый снимок ставки.
- В выдаче поиска до отправки запроса показываются текущие ставки машин.
- После `confirm-terms` / оплаты объём и цену в MVP через API не меняют; «доп. соглашение» mid-job — не в MVP (спор или новый заказ).
- Частичный возврат / частичная выплата за неполный объём — отложено (§17; `ORDER_STATE_MACHINE.md` §5.5): в споре до выплаты только полный возврат или полная выплата.
- Исполнитель подтверждает условия отдельной кнопкой после первого «принять» (1 сутки).

Запрос на ожидании ответа — только одному исполнителю. Клиент может снять его до принятия/отказа и выбрать другого. Исполнитель, который отказал или не ответил 5 минут, по этому заказу в выдаче не показывается.

## 6) Телефон, валюты и провайдеры (задел на расширение)

Мультирынок в продукте **не** строится через IP, «страну устройства» или экран «регион недоступен» на старте. Два независимых гейта:

1. **Вход** — умеем ли доставить OTP на введённый номер. Пока пользователь вводит телефон, клиент дергает бэкенд; если под номер нет настроенного OTP-провайдера → сообщение, что с такими номерами пока не работаем. Отдельного allowlist стран в UI нет: решение = «есть ли адаптер/конфиг под этот номер».
2. **Деньги** — у тарифов, заказа и платежа есть `currency` (ISO 4217). Платёжный провайдер для `secure_deal` выбирается **по валюте**. В MVP активна одна валюта `RUB` → ЮKassa. Матч клиентов и исполнителей — по **адресу и расстоянию**, не по стране номера.

При расширении на другие страны/валюты: добавить валюту в справочник, привязать провайдера, который принимает оплату и выплачивает на карты нужной зоны; отдельно расширить покрытие OTP. Кросс-валютные / кросс-провайдерные коридоры (клиент платит в одной валюте, исполнитель получает в другой) **пока не проектируем** — зафиксировать, когда появится вторая валюта.

## 7) Требования к платежной архитектуре

Оплата через приложение не обязательна для каждого заказа, но интеграция с ЮKassa («Безопасная сделка») входит в первый релиз (валюта `RUB`).

Нужен абстрактный платежный слой:

- интерфейс `PaymentProvider` (адаптер провайдера);
- выбор конкретного адаптера по `currency` заказа (справочник валют → `provider_code`);
- сервис `PaymentService` (прикладные сценарии);
- обработчик платежных вебхуков и событий;
- синхронизация платежных статусов.

Функции, которые должны поддерживаться архитектурно:

- создание платежа;
- резервирование/холд;
- списание/подтверждение;
- отмена;
- возврат;
- выплата исполнителю;
- комиссия платформы;
- статусы «Безопасной сделки».

Источник истины по реальным денежным средствам — внешний платежный провайдер, а не баланс в базе данных.

После `captured` платформа деньги больше не двигает и не компенсирует «из кармана»; админ — только санкции; в UI возврат после выплаты не обещать.

## 8) «Безопасная сделка» как опциональный модуль

«Безопасная сделка» включается по выбору клиента и не должна быть обязательной по умолчанию.

Целевой поток:

1. клиент выбирает безопасную сделку;
2. исполнитель подтверждает условия (посчитанная сумма); без привязанной карты для выплат — нельзя;
3. `awaiting_payment`, форма оплаты, 1 сутки; допускается несколько попыток оплаты (история `payment_records`, одновременно не больше одной живой `pending` / `authorized`);
4. клиент платит посчитанную сумму **плюс комиссию сделки** (комиссия провайдера, видна на экране отправки при включении сделки); оплата зачисляется на баланс сделки ЮKassa (холд); при заказе ещё в `awaiting_payment` успех → срочный `in_progress` / плановый `scheduled`. Неудачная попытка (`failed`) заказ не двигает — можно платить снова. Поздний успех, когда заказ уже отменён или снова в поиске — автовозврат (`ORDER_STATE_MACHINE.md` §5.4);
5. обе стороны подтверждают исполнение → выплата исполнителю посчитанной суммы на привязанную карту;
6. спор до выплаты — деньги по решению админа; после выплаты — только санкции;
7. истёк срок сделки у провайдера (180 дней) → деньги возвращены клиенту, заказ `disputed` **только если** оплата была (`authorized`);
8. несколько споров на заказ (история); одновременно один открытый; одна апелляция на каждый спор;
9. комиссия платформы.

Если клиент не создал ни одной попытки оплаты — провайдер ничего не возвращает; наш таймаут (1 сутки) возвращает заказ в поиск исполнителя.

Правка деталей на `awaiting_payment` — вернуть/отменить **живую** попытку оплаты, снова переговоры. Подробности — `ORDER_STATE_MACHINE.md` §5.

## 8.1) Подписка исполнителя (`executor_subscription_enabled`)

В MVP флаг **выключен**.

Когда включён — без активной подписки исполнитель не в поиске и не принимает заказы.

**Автоактивация после оплаты (целевой вариант под флагом):** отдельный платёж (не холд заказа), webhook → `active` + срок, по истечении `expired` и скрытие из поиска. Нужны: продукт подписки в ЮKassa, `POST /executor/subscription/pay`, идемпотентный webhook, джоба expiry.

**Через админку:** админ ставит `active` / срок вручную (оплата вне приложения или без оплаты). Нужны: экран очереди, аудит. Медленнее, зато без рекуррента.

Лицензии подтверждает админ отдельно, не смешивать с оплатой подписки.

Модуль должен быть изолирован так, чтобы MVP можно было запустить без него и безопасно подключить позже.

## 9) Правила назначения

На ожидании первого ответа — один исполнитель. Не ответил за 5 минут = отказ, повторно на этот заказ нельзя.

Первое «принять» открывает контакты. Если принят срочный заказ — остальные ожидающие срочные запросы этого исполнителя закрываются автоотказом, клиенты получают уведомление, их заказы остаются в поиске; плановые запросы висят до ответа. «Подтвердить условия» (1 сутки) → `direct_payment` / холд: **срочный** сразу `in_progress`, **плановый** → `scheduled`, в `planned_start_at` авто → `in_progress`. `completed` — когда обе стороны подтвердили исполнение. На этом заказе после фиксации сделки (`scheduled` / `in_progress`) нового поиска нет.

Минимальные технические гарантии:

- конечный автомат заказа;
- не более одного ожидающего ответа кандидата на заказ;
- идемпотентный API принятия;
- одновременные действия по одному заказу сериализуются блокировкой строки; кто побеждает (клиент vs «принять», таймер vs «отказаться», клиент vs «подтвердить условия», оплата vs отмена, фора 30 с на условия) — `ORDER_STATE_MACHINE.md` §7;
- запись об отказе, автоотказе и таймауте запрещает повторный запрос этому исполнителю на этот заказ; после снятия клиентом (`withdrawn`) — тот же кандидат снова `notified` (одна строка на пару в БД).

## 11) Черновые модели статусов

### Статус заказа

- `draft` — сохранён без запроса
- `published` — поиск исполнителя (в том числе после срыва матча до работы)
- `in_negotiation` — контакты, правки, «подтвердить условия»
- `awaiting_payment` — ждём холд (`secure_deal`)
- `scheduled` — плановый подтверждён/оплачен, ждёт `planned_start_at`
- `in_progress` — работа идёт, пока обе не подтвердят исполнение или спор
- `completed` — обе подтвердили
- `disputed` — спор
- `cancelled` — отмена клиентом до работы, отмена планового на `scheduled`, «исполнитель не найден», отмена админом или исход спора

### Статус платежа (только для `secure_deal`)

У заказа с `direct_payment` записей оплаты нет (логически «не требуется»). Статусы **строки** `payment_records`:

- `pending`
- `authorized`
- `captured`
- `failed`
- `cancelled`
- `refunded`

## 12) Модели монетизации для проверки

Нужно проверить минимум три варианта:

1. подписка для исполнителей;
2. комиссия с «Безопасной сделки»;
3. гибридная модель.

«Безопасная сделка» доступна с первого релиза, комиссия платформы с неё включается на этапе 2. Подписка — под флагом.

## 13) Отдельный трек исследования для России

Перед запуском «Безопасной сделки» отдельно проверить:

- какие провайдеры в РФ поддерживают marketplace/split-сценарии;
- юридическую модель движения средств и комиссии;
- требования KYC/KYB и роли участников;
- ответственность по спорам и возвратам;
- налоговые и бухгалтерские последствия выбранной схемы;
- **срок жизни холда — решено.** Обычный двухстадийный платёж ЮKassa живёт до 7 дней — для `month` и долгих `day` мало. Используем «Безопасную сделку»: деньги лежат на балансе сделки до 180 дней (срок задаётся один раз для магазина), выплата исполнителю — по завершении. Ограничений по тарифу нет.

## 14) Рекомендуемый поэтапный запуск

Этап 1 (быстрая проверка гипотезы):

- вход, контакты пользователя, аватар и парк исполнителя;
- поиск исполнителей (карта/список), запрос одному, таймер 5 минут, переговоры, завершение;
- спор (тред в приложении, закрытие в админке);
- внутренние рейтинги без UI;
- прямой контакт и прямая оплата вне приложения;
- опциональная «Безопасная сделка» через ЮKassa (выплата исполнителю на карту после `completed`), без комиссии платформы;
- плановый заказ.

Этап 2:

- запуск комиссии платформы.

Этап 3:

- B2B-надстройки только при подтвержденной потребности.

## 15) Непересматриваемые архитектурные ограничения

- Один аккаунт может быть и клиентом, и исполнителем. Роль в UI — `current_mode`.
- У одного исполнителя неограниченное число единиц техники.
- Каталожные тарифы задаёт исполнитель и они принадлежат единице транспорта.
- Запрос на ожидании ответа — только одному исполнителю на заказ.
- После отказа, автоотказа и таймаута 5 минут исполнитель не запрашивается повторно на этот заказ.
- Жёсткого календаря нет; окна задаёт заказчик; пересечение → warning, не блок; срочные — ещё флаг исполнителя.
- Свою технику заказать нельзя.
- После фиксации сделки (`scheduled` / `in_progress`) поиск исполнителей на том же заказе не продолжается. До этого срыв матча возвращает тот же заказ в поиск; полную отмену до фиксации делает только клиент (на `scheduled` — обе стороны).
- Внутренние рейтинги не отображаются в UI.
- Доступ по телефону определяется наличием OTP-провайдера под номер, а не IP/«регионом устройства».
- Валюта денежных сущностей явная (`currency`); провайдер `secure_deal` выбирается по валюте. В MVP — `RUB` → ЮKassa.
- Матч — по геолокации заказа и машин, не по стране телефонного номера; на проде геопоиск через PostGIS (`TECH_STACK.md`).
- Платежный провайдер остается источником истины по деньгам; webhook + регулярный reconcile догоняют статусы. После выплаты админ деньги не двигает.
- «Безопасная сделка» остается опциональной и модульной.
- Ценообразование заказа остается расширяемым по типам тарифов.

## 16) Сроки в правилах сервиса

Текст правил — `SERVICE_RULES.md`:

- 5 минут на ответ исполнителя;
- 1 сутки на подтверждение условий;
- 1 сутки на оплату безопасной сделки (иначе возврат в поиск);
- 1 сутки на второе подтверждение исполнения, иначе автоприёмка;
- 24 часа бездействия в поиске для срочного заказа, для планового — до даты начала.

## 17) Отложено (после architecture review)

| --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Жёсткий календарь** (запрет принять / confirm при пересечении, буферы между заказами, слоты в UI) | Окна заказчика + скрытие в поиске + warning (`SEARCH_ALGORITHM.md` §6) | Не раньше, чем мягкие окна поработают на реальных заказах **и** двойные брони станут заметной болью (или отдельное продуктовое решение «ужесточаем»).
