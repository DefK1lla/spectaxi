# Пользовательские сценарии (MVP)

## 1) Цель документа

Пользовательские сценарии SpexTaxi. Шаги взяты из продуктового плана и уточнений. Не описанные ветки не добавляются.

Поток заказа одинаковый для частного и регулярного бизнес-клиента. Плановый заказ входит в MVP.

## 2) Кто действует

Один пользователь — один аккаунт. В этом аккаунте можно быть:

- клиентом (частным или регулярным бизнес-клиентом; отдельной сущности компании в MVP нет);
- исполнителем (владелец/водитель спецтехники).

После входа по телефону — форма регистрации: имя и **режим** (`клиент` или `исполнитель`). Это сразу `current_mode`. Других полей роли (`default_mode`, флаги «включён клиент / исполнитель») нет. Интерфейс (меню, заказы, поиск / парк) зависит от `current_mode`. Переключение режима остаётся; при первом переключении на исполнителя создаётся `executor_profile`.

Контакты заполняют оба. На форме **всегда** видны: телефон для связи, Telegram, WhatsApp, MAX — по отдельности не обязательны. Можно добавить ещё мессенджеры (название + ссылка). Для создания и принятия заказа нужны **имя** и **хотя бы один** канал связи (телефон или любой мессенджер). Иначе предупреждение и ссылка в профиль.

**В поиске и до первого «принять» контакты не показываются.**

Свою технику запросить нельзя.

Внутренние рейтинги (`RATING_PLAN.md`) в UI **не показываются**. После завершённого заказа стороны оставляют друг другу **публичные отзывы** (звёзды и необязательный текст). Причины — `CANCELLATION_REASONS.md`. Правила сервиса и блокировка — `SERVICE_RULES.md`. Поиск — `SEARCH_ALGORITHM.md`.

У клиента и исполнителя есть экран всех уведомлений (перечень — раздел 13). У исполнителя — список входящих (не только пуш).

## 3) Вход и регистрация

1. Указать номер телефона. Пока вводит — приложение спрашивает API (`GET /auth/phone-support`): есть ли OTP-провайдер под этот номер. Если нет — сообщение вроде «пока не работаем с номерами этой страны», дальше нельзя. IP и «регион устройства» не проверяем.
2. Получить код подтверждения: в Telegram, если номер там зарегистрирован, иначе по SMS (тот же критерий покрытия провайдера).
3. Ввести код.
4. Если новый пользователь — имя и режим (`клиент` / `исполнитель`) → `current_mode`.

## 4) Клиент: фильтр, поиск и запрос

Срочный и плановый поток один по кнопкам. Алгоритм выдачи и занятость по окнам — `SEARCH_ALGORITHM.md` §6. Жёсткий календарь отложен — `PRODUCT_FOUNDATION.md` §17.

Сначала **фильтр заказа** (его же можно сохранить как черновик):

- категория транспорта (из БД);
- нужный тариф из разрешённых категории — у одних типов это часы / смены / сутки / месяцы, у других километры и рейсы (`TARIFF_TYPES.md`);
- количество по выбранному тарифу;
- режим: срочный или плановый;
- для планового — **начало и конец** окна работ (к какому моменту заказ должен быть выполнен); оба обязательны, конец позже начала;
- для срочного — даты начала нет; опционально «нужно завершить к» (`planned_end_at`);
- точка работ;
- описание (свободный текст, необязательно);
- максимальная цена — **необязательно**.

Система считает стоимость по каждой машине: `ставка тарифа × количество`. Сумму никто не вписывает вручную.

1. Поиск: карта и список по фильтру. Сортировка списка — ближайший первый, при равной дистанции — дешевле. Для **срочного** — только с флагом «принимаю срочные заказы». Исполнители, у которых окно **этого** поиска пересекается с уже принятыми заказами, **не показываются**. Клиент сужает выдачу: расстояние и потолок цены.
2. Карточка — единица транспорта: фото, локация, аватар и имя, посчитанная цена, публичные отзывы об исполнителе. Контактов нет.
3. Карта: точка машины, совпадение координат — `+N` и список снизу.
4. Экран машины и исполнителя, контакты скрыты.
5. Экран отправки запроса. Здесь же переключатель **«Безопасная сделка»** (флаг `secure_deal_enabled` включён с первого релиза; переключатель по умолчанию выключен — прямой расчёт). При включении видно: цена, комиссия сделки и итог к оплате — комиссию платит клиент, исполнитель получает цену без вычетов. Отправить запрос **этой** машине / исполнителю. Нельзя свою единицу. Нельзя машину без подтверждённой лицензии категории (её нет в выдаче).
6. Ждать ответ. На плановый заказ те же **5 минут**.

Запрос можно не отправлять, а **сохранить как черновик**. Черновики — отдельная вкладка на экране заказов. Отправка черновика («опубликовать») переводит его в поиск **без** выбранного исполнителя: дальше клиент открывает выдачу и шлёт запрос выбранной машине уже внутри этого заказа.

Пока исполнитель не принял и не отказал, клиент может снять запрос и выбрать другого. После снятия этого же можно запросить снова. После отказа — скрыт по заказу, повторно нельзя. Не ответил за 5 минут — это отказ: скрыт, повторно нельзя. На один заказ одновременно ждёт ответа только один запрос.

Пока ожидающего запроса нет, клиент может править фильтр заказа (тариф, количество, окно начала/конца, адрес, описание, режим расчёта) прямо в поиске — в выдаче цены по **текущим** ставкам машин. После отправки запроса ставка в заказе зафиксирована снимком (`PRODUCT_FOUNDATION.md` «Цена заказа»). Начало планового — только в будущем; конец — позже начала.

Если исполнитель тем временем принял **другой срочный** заказ, а этот заказ тоже срочный — клиенту уведомление «исполнитель отказался», заказ остаётся в поиске, этот исполнитель по нему скрыт. Плановый запрос в этом случае продолжает ждать ответа.

Пока заказ не в `scheduled` / `in_progress`, любой срыв матча возвращает его к поиску исполнителя. После фиксации сделки поиск на **этом** заказе не продолжается. Нужен новый заказ («такой же»).

**Заказ в поиске не висит бесконечно.** Если исполнитель так и не найден:

- срочный — через **24 часа без действий клиента** по заказу (отправка запроса и правка заказа сбрасывают отсчёт), когда нет ожидающего запроса;
- плановый — при наступлении **даты и времени начала**, если заказ всё ещё в поиске (ожидающий запрос, если есть, сначала дожидается ответа или 5 минут).

Заказ отменяется системой, штрафа никому нет, клиенту уведомление «исполнитель не найден» с кнопкой «искать снова?».

## 5) Исполнитель: настройки, парк, лицензия, подписка

### 5.1. Флаг «принимаю срочные заказы»

Один чекбокс на экране профиля исполнителя. Меняет его **только сам исполнитель, вручную**; система его не переключает ни при принятии, ни при завершении заказа.

- Включён — исполнитель виден в поиске по срочным заказам.
- Выключен — в поиске по срочным его нет; по плановым он виден по-прежнему.

Флаг относится к исполнителю целиком, а не к отдельной машине. Видимость в поиске ещё зависит от подписки (если флаг подписки включён) и лицензии категории машины.

### 5.2. Подписка

Флаг `executor_subscription_enabled`. В MVP флаг **выключен**: активация исполнителя без оплаты. Когда флаг включён — для приёма заказов нужна оплаченная подписка (автоактивация после оплаты, см. `PRODUCT_FOUNDATION.md`).

### 5.2.1. Карта для выплат

В профиле исполнителя — «Карта для выплат». Карту вводят в форме ЮKassa; приложение хранит только маску номера (`•••• 1234`). Карту можно заменить или удалить (кроме случая, когда по его заказу со сделкой ещё ждёт выплата).

Без карты исполнитель принимает запросы и работает с прямым расчётом, но не может «подтвердить условия» по заказу с безопасной сделкой — ссылка в профиль. В карточке входящего запроса видно, что заказ со сделкой.

### 5.3. Добавление транспорта

Лимита нет. Категории — строки таблицы `machinery_categories`, их создаёт админ. У строки: системный `code` типа транспорта, обязательный тип лицензии из справочника `license_types`, текст для интерфейса, разрешённые тарифы. Отдельного JSON-конфига лицензий нет: конфиг — сама строка типа.

При добавлении:

- категория (селект из таблицы типов);
- фото **файлами**, минимум **одно**;
- локация (автокомплит, в том числе адреса других его машин);
- тарифы из списка, разрешённого категории.

Без **верификации админом** (`approved`) на **эту категорию** машину сохранить можно, в поиске её нет. Комплект на категорию (на все машины этой категории): **водительские права** нужного типа + **документ на право пользования техникой** (любой подтверждающий). Срока у лицензии в системе нет. Админ в админке: типы лицензий, типы транспорта, очередь pending / approved / rejected.

Тарифы принадлежат единице. Справочник — `TARIFF_TYPES.md`. Изменение ставки на машине не меняет уже отправленные заказы: `unit_rate` — снимок на момент отправки запроса (`PRODUCT_FOUNDATION.md` «Цена заказа»).

## 6) Исполнитель: первое «принять»

Входящие — список заказов и уведомления. Открытие заказа из уведомления **не** отдельный статус: смотреть можно, но «просмотрел» никуда не пишется. В карточке видны окно работ (начало/конец у планового; у срочного — «нужно к», если указано).

Одному исполнителю могут одновременно висеть запросы от разных клиентов (если окна поиска их не исключили).

1. Заказ без контактов заказчика: детали, цена, средняя оценка и число отзывов о заказчике (без текста отзывов). «Принять запрос» / «Отклонить». 5 минут, в том числе на плановый. Если окно этого заказа пересекается с другими его уже принятыми заказами — **предупреждение**, принять всё равно можно (`SEARCH_ALGORITHM.md` §6).
2. «Принять запрос» — контакты открываются, статус `in_negotiation`. Это **не** фиксация условий.
   - Принял **срочный** — все его остальные ожидающие **срочные** запросы (по любой его машине) автоматически закрываются, их клиентам уведомление «исполнитель отказался», те заказы остаются в поиске. Ожидающие **плановые** запросы висят дальше.
   - Принял **плановый** — остальные запросы не трогаются.
3. «Отклонить» — причина стадии, исполнитель скрыт по заказу.
4. Таймаут 5 минут — как отказ: исполнителю **−3**, скрыт по заказу, повторно нельзя.
5. Если контактов не хватает (нет ни телефона, ни мессенджера) или нет имени — принять нельзя, ссылка в профиль.

После «принять» экран **другой**: детали заказа, контакты заказчика, кнопка **«Подтвердить условия»** (не повтор «принять»). Срок подтверждения условий — **1 сутки**.

## 7) Переговоры и фиксация условий

Статус `in_negotiation`. У заказчика — правка деталей (тариф, количество, окно начала/конца, адрес, описание). Количество пересчитывает сумму от **сохранённой** ставки; смена типа тарифа — новый снимок ставки с машины. После сохранения `details_version` растёт, исполнителю уведомление, его «подтвердить» сбрасывается, дедлайн подтверждения условий снова 1 сутки. Подтверждение со старой версией — ошибка.

У исполнителя — «Подтвердить условия» (текущая посчитанная сумма) или **«Отклонить партнёра»** с причиной. При пересечении окон с другими его заказами — снова предупреждение, подтвердить можно. На переговорах и оплате полностью отменить заказ клиенту он **не может** (только отклонить партнёра → поиск). На `scheduled` отмена с причиной уже можно (раздел 8).

Не подтвердил за сутки (+ **30 секунд форы** после дедлайна, `ORDER_STATE_MACHINE.md` §7) — заказ `published`, исполнитель скрыт, исполнителю **−3**.

«Отклонить партнёра» есть у обеих сторон на `in_negotiation` и на `awaiting_payment`: заказ `published`, исполнитель скрыт, клиент ищет другого **в этом заказе**. Спора нет. Если на `awaiting_payment` есть **живая** попытка оплаты (`pending` / `authorized`) — её отменяют или холд возвращают; прошлые неудачные попытки (`failed` и т.п.) остаются в истории.

После «Подтвердить условия»:

- **срочный** + `direct_payment` — сразу `in_progress`, создаётся назначение;
- **плановый** + `direct_payment` — `scheduled` (ждём дату начала), создаётся назначение;
- `secure_deal` — нужна карта для выплат у исполнителя (раздел 5.2.1). `awaiting_payment`: форма оплаты у клиента, у исполнителя «не оплачен». Срок **1 сутки**. Можно несколько попыток оплаты (каждая — своя запись). Карта отклонена / клиент закрыл форму (`failed`) — заказ **остаётся** `awaiting_payment`, можно платить снова. Успешная оплата → **срочный** `in_progress`, **плановый** `scheduled`. **Не оплатил за сутки** → живую попытку отменяют, клиенту **−3**, заказ **возвращается к поиску** (не отменяется).

На `awaiting_payment` заказчик может писать исполнителю через открытые контакты (и наоборот). Правка условий на этом статусе: вернуть/отменить живой холд или незавершённую попытку, снова `in_negotiation` (версия++, исполнителю снова подтверждать).

## 8) Работа и завершение

**Плановый до начала (`scheduled`).** После условий/оплаты плановый заказ не в «работе», а в `scheduled`. До `planned_start_at` обе стороны могут отменить с причиной → `cancelled`, при сделке холд возвращается. Отменил исполнитель — клиенту уведомление с «искать снова?». В момент `planned_start_at` статус сам становится `in_progress` (кнопки «начал работу» нет). Спор на `scheduled` нельзя.

**`in_progress`.** Пока **обе** стороны не подтвердят исполнение либо не откроют спор. Отмена кнопкой **нельзя** — только спор. Если исполнитель не вышел на объект — клиент сам решает, в том числе может открыть спор. У срочного после условий/оплаты сразу `in_progress`, окна `scheduled` нет.

У обеих кнопка «работа выполнена». Когда нажали оба — `completed`, выплата при сделке, можно оставить отзыв.

Если один подтвердил, второй молчит **1 сутки** — автоподтверждение молчащего, заказ `completed` (работа считается выполненной). Если вторая сторона в течение этих суток открыла спор — спор главнее: заказ `disputed`, автоприёмки нет.

- Молчал **клиент** — клиенту **−3**, исполнителю **+5** за успех; клиенту **+3** за успех нет.
- Молчал **исполнитель** — исполнителю тоже **−3**, и всё равно закрытие **в его пользу** (работа по сути сделана); клиенту **+3**, исполнителю **+5** за успех.

Спор с `in_progress` и с `completed`. При прямом расчёте у исполнителя есть причина «заказчик не оплатил работу».

Кнопка «такой же заказ» на `completed` — после того как обе стороны подтвердили (или автоподтверждение). На `cancelled` — после отмены. Если заказ вернулся к поиску, «такой же» не нужен.

## 9) История

Активные — без `cancelled` и без черновиков (черновики на своей вкладке). Архив: фильтр отменённых. Завершённые и `disputed` видны. Заказы в поиске (`published`) — в активных.

## 10) Отмена

Полная отмена кнопкой — **у клиента**: `draft` (удалить черновик), `published` (без причины; ожидающий запрос снимается, исполнителю уведомление), `in_negotiation`, `awaiting_payment` (с причиной стадии), `scheduled` (с причиной стадии). На `awaiting_payment` / `scheduled` живую попытку оплаты (`pending` / `authorized`) отменяют или возвращают, затем заказ `cancelled`.

У **исполнителя** на переговорах и оплате полной отмены нет — только «отклонить партнёра» (заказ обратно в поиск). На `scheduled` исполнитель тоже может отменить с причиной (раздел 8).

Нельзя кнопкой: `in_progress` (только спор), `completed`, `disputed` (только админ).

Системные отмены: исполнитель не найден (раздел 4), отмена админом. Штрафа нет.

После полной отмены — «искать снова?» (новый заказ).

## 11) Спор

Только `in_progress` и `completed` (с `completed` — в течение **2 суток**). На заказ — **несколько** споров в истории; одновременно открыт только один. Сообщения — в отдельной таблице на каждый спор. После закрытия можно: **апелляция** того же спора (лимит 1 на спор) **или** новый спор с новой причиной (если ещё в окне / заказ ещё `in_progress`). Пока есть `open` спор — заказ `disputed`, автоприёмка снята; выплата по сделке не идёт, пока спор открыт (админ может закрыть в `completed` с выплатой, если холд ещё `authorized`). После выплаты (`captured`) новый спор в окне ещё можно; деньги платформа не возвращает — санкции при доказанной вине (`ORDER_STATE_MACHINE.md` §5.5; компенсация отложена — `PRODUCT_FOUNDATION.md` §17). Тикеты поддержки не по заказу в MVP нет.

Причина при открытии, при `other` текст. Фото — во вложении **сообщения**. Админ пишет и закрывает только из админки (`completed` / `cancelled` / `in_progress` / `scheduled`).

Автоматически в `disputed`:

- истёк срок сделки у провайдера (180 дней) и он вернул клиенту **уже оплаченные** деньги (платёж был `authorized`);
- пришло «оплата прошла», а заказ уже в странном статусе (не `awaiting_payment` / не обычная отмена в поиск) — см. `ORDER_STATE_MACHINE.md` §5.4.

Если сигнал об оплате пришёл, когда заказ уже `cancelled` или снова `published` — деньги **автоматически возвращают**, в спор не открывают. Если клиент так и не платил — провайдер ничего не возвращает, срабатывает наш таймаут с `awaiting_payment` → поиск.

Пока холд не выплачен, админ может направить деньги (выплата / возврат). Если выплата уже ушла (`captured`), админ деньги **не контролирует** — только санкции к пользователям; закрытие такого спора в `cancelled` возврата не делает.

## 12) Отзывы

После `completed` у обеих сторон: оценка **1–5 звёзд** и необязательный текст. Отзывы об исполнителе видны в профиле / карточке исполнителя и в карточке машины в поиске. Отзывы о клиенте исполнитель видит в карточке входящего запроса как среднюю оценку и число отзывов. Это не внутренний рейтинг.
